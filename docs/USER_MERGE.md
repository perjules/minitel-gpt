# Repair a misspelled profile: offline SSH merge

Use `scripts/merge_users.py` for exceptional cleanup. It merges an existing named
source into an existing named destination, then deletes the source identity.
It never resolves an unknown name by creating another profile. Use numeric IDs
from `--list`; the default MinitelGPT/household profile cannot be either endpoint.
No web page, model/API call, mail notification or deployment helper is involved.

## Use

Run as the normal `minitel` account from the checkout on the Pi. Do not run
`uv sync` against the Pi's managed `.venv`. The script reads MINITEL_MEMORY_DIR
from the environment or the checkout's `.env`; `--data-dir` overrides it.

```sh
cd ~/minitel-gpt
.venv/bin/python scripts/merge_users.py --list
```

For example, if #7 is the misspelled profile and #2 is the correct profile:

```sh
.venv/bin/python scripts/merge_users.py --source 7 --target 2
```

Without `--apply` this is a read-only preview: names, direction, memory/pending
counts, aliases policy and presence of source journal/drafts. It does not create
folders/profiles, migrate JSON, modify memory or contact systemd/providers.
Memory schemas 1 and 2 are accepted without upgrading during preview.
Check the displayed **SOURCE SUPPRIMÉE** and **DESTINATION CONSERVÉE**.

Stop both services and close any independent terminal/test console processes.
Run only one merge at a time. Application sessions must not access these folders
while filesystem changes and the SQLite transaction are being coordinated.

```sh
sudo systemctl stop minitel-chatgpt admin-ui
.venv/bin/python scripts/merge_users.py --source 7 --target 2 --apply
```

`--apply` independently verifies both services report inactive/failed. It will
refuse if a service is active, transitioning, unknown, or cannot be checked.
It does not stop/restart services or bypass authentication itself. Once it reports
**Fusion terminée**, start the apps and open a fresh profile session:

```sh
sudo systemctl start minitel-chatgpt admin-ui
```

The source's old names/aliases now select the destination instead of creating the
same accidental user again. It has no remaining separate profile. The source ID
is retained in the allocator's history and cannot be reused by later creations.

## Exact merge policy

- All saved source facts, preferences, notes, list items and tasks are appended,
  including completed items, full long text, origin, timestamps and source quotes.
  IDs stay unchanged unless already used at the destination; collisions get new
  IDs. The archive records the mapping. Existing vectors follow the same text.
- Imported source facts become private and require fresh publication review under
  the destination’s identity. Unchanged destination facts retain their sharing.
  See [PROFILE_SHARING.md](PROFILE_SHARING.md).
- Duplicates and contradictions are retained. No AI decides which version is
  correct, and nothing is silently truncated or discarded. Review/correct these
  records in the normal admin editor after restarting.
- Pending eligible statements from both profiles are retained with their original
  event/session IDs and aligned to the new destination barrier. They become ready
  for a later normal extraction trigger; the script never invokes extraction.
  Destination learning settings remain in effect. Combined memory must fit the
  normal 256-item/1-MiB limit and pending statements must fit 48; otherwise the
  merge is refused before any data is removed.
- Destination display name, enabled status, Gmail/PRONOTE assignments and welcome
  checklist/completion stay in place. Its saved language wins; if absent, the
  source language is used. Old temporary welcome dialogue is archived and cleared
  to avoid reusing stale conversational context. Source welcome progress/history
  is also archived, not replayed or automatically learned.
- Source aliases transfer to the destination. An obsolete source alias
  `MinitelGPT` is retired instead, so that reserved selector returns to default #1.
  Source service grants are removed,
  **not unioned** with destination privileges. External accounts/credentials and
  other users survive. No creation/deletion email report is generated by this
  offline repair. Neither endpoint may be the global household profile.
- Destination user revision, memory revision and barrier advance; both old leases
  are invalidated. Existing sessions must reopen. Delayed source or destination
  work cannot overwrite the merge or recreate the deleted identity.

## SQL sessions

Ordinary SQL sessions and messages transfer to the destination, retaining IDs and
source links. Old live source/destination sessions become interrupted; both old
profile revisions lose write access. Eligible pending statements cross the merge
barrier; superseded statements stay superseded. Import checkpoints follow copied
JSONL filenames, preventing duplicate import of already archived history. Deleting
the source therefore cannot cascade away transferred transcripts. Session sharing
is never implied by fact sharing. See [SESSIONS.md](SESSIONS.md).

## Files and private modes

The entire source profile directory moves to:

`<data-dir>/<destination-key>/merged-profiles/<source-id>/`

The source's JSONL conversations are additionally copied into the destination's
normal `logs/`, with `merged-<source-id>-` filename prefixes, never overwriting an
existing file. Legacy JSON and other original files remain in the archived
source directory. `merge-source.json` preserves the source ordinary-memory
snapshot, pending statements, welcome state, aliases and memory-ID mapping.

The destination journal and drafts are untouched. A source `journal.md.enc`
stays **encrypted, byte for byte**, with its original owner ID/password; it is
not silently combined with another journal or exposed in ordinary memory. It is
no longer the active journal of a separate profile. The existing standalone
`scripts/journal.py export` can read the archived encrypted file using its original
password, if its owner later needs to recover it. This would be an explicit
plaintext export, separate from this merge.

Source mail recovery drafts are also retained as archived files, without
pretending their original profile/account binding is valid for automatic restore
under the destination. No journal decryption, password reset, credential transfer
or Rose ingestion is performed.

## Backup, failure and recovery

Before importing any legacy JSON or changing live data, the script creates a
private directory under `<data-dir>/merge-backups/<timestamp>-<random>/`:

- `users.sqlite3`: a SQLite backup of the whole registry/memory database.
- `source/` and `target/`: complete copies of the two original profile directories.
- `status.json`: source/target IDs and keys, and `started`, `complete`, or
  `rolled_back` status. The command prints the backup path on success.

This backup contains ordinary personal data and may contain encrypted journals
and plaintext archived mail drafts. Keep it under the same local access rules as
the application data. Backups are retained; cleanup is an explicit later action.
They are not part of ordinary admin memory exports or per-profile deletion.
Ensure space is available for the database and both directories before applying.

Detected failures roll back the SQLite transaction, restore a moved source
folder and remove only files created by the failed merge. A successful legacy
compatibility import may remain; its original bytes are still backed up. The
script never restores the full database automatically over other users' work.

SQLite and the filesystem do not share a crash-atomic transaction. A killed
process, power loss, or failed rollback leaves a `started` status. Further merges
are refused until that backup is inspected. **Keep the services stopped** while
recovering; do not blindly retry or discard the marker.

For an interrupted operation before any app has resumed, restore the backup's
`users.sqlite3` and both `source/` and `target/` directories to the database path
and keys recorded in `status.json` (move the current copies aside first, rather
than overlaying trees). Move any `users.sqlite3-journal`, `users.sqlite3-wal` and
`users.sqlite3-shm` sidecars aside with the old database too, so they cannot be
replayed against the restored database. A full DB restore also restores other users to the backup
instant, so do not do this blindly if anything has run or changed since then.
After verifying the recovered pair and database, retain the backup and mark its
status `rolled_back` before another merge. If only the backup's initial copy
failed, live profiles may be untouched; inspect them before deciding to restore.
A completed SQL merge whose final status write failed must be verified as such;
do not merge the same source again or recreate it.

Offline tests use synthetic profiles/files and mocked systemd checks, including
ID collisions, provenance/vectors, pending queues, old-session fences, legacy
preview/import, foreign keys, permission isolation, symlink refusal, rollback
and post-commit status failure. Physical SSH/Pi execution remains a manual check.

Validation on 31 October 2026: locked all-extras sync; **1019 tests and 400
subtests passed**, including 21 merge cases. Ruff, requirements-export freshness
and whitespace checks passed. No real profile merge, provider operation or Pi
service/deployment action was performed during development.
